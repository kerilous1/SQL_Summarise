Core SQL Commands & Concepts

The question set is grounded in the Oracle HR schema and covers five major SQL command families, progressively building from simple retrieval to correlated multi-table operations.

All solutions assume the Oracle HR schema tables: employees, departments, locations, jobs, countries, regions. INSERT statements generate IDs using MAX(employee_id)+1.

1. SELECT — Data Retrieval

The workhorse of SQL. The questions cover three escalating levels of SELECT complexity.

Basic SELECT with WHERE filter ▾

Direct conditions on column values. Operators: =, <, >, BETWEEN, LIKE, IS NULL, IS NOT NULL.

SELECT first_name, last_name, salary
FROM   employees
WHERE  salary BETWEEN 4000 AND 9000;   -- Q36, Q113

SELECT first_name, last_name, commission_pct
FROM   employees
WHERE  commission_pct IS NULL;              -- Q47, Q161
ORDER BY — Sorting results ▾

Sort by one or more columns. DESC reverses order. Sorting can reference joined table columns.

SELECT first_name, last_name, salary
FROM   employees
ORDER BY salary DESC;                      -- Q6

ORDER BY d.department_name, e.salary;      -- Q149: multi-column sort
GROUP BY + HAVING — Aggregation with filtering ▾

GROUP BY collapses rows into groups; HAVING filters groups (after aggregation). Always used with aggregate functions: COUNT, SUM, AVG, MAX, MIN.

SELECT   d.department_name, AVG(e.salary) avg_salary
FROM     employees e
JOIN     departments d ON e.department_id = d.department_id
GROUP BY d.department_name
HAVING   AVG(e.salary) > 7000;             -- Q7

HAVING   COUNT(e.employee_id) > 5;          -- Q19: row count filter
HAVING   SUM(e.salary) > 40000;             -- Q27: sum filter

2. Subqueries — Queries within Queries

The most heavily tested concept. Subqueries appear in WHERE, HAVING, FROM, and even SELECT clauses.

Single-value scalar subqueries ▾

Returns exactly one value. Used with comparison operators =, <, >. The most common pattern — appears in ~60 questions.

-- Pattern: compare to a specific employee's attribute
WHERE salary > (SELECT salary FROM employees WHERE employee_id = 130)

-- Pattern: compare to an aggregate (AVG, MIN, MAX)
WHERE salary = (SELECT MIN(salary) FROM employees)

-- Pattern: compare date attributes
WHERE hire_date < (SELECT hire_date FROM employees WHERE employee_id = 120)
Correlated subqueries — row-by-row evaluation ▾

References the outer query's current row. More powerful but slower. Used to compare each row to its own department/job group average. Key pattern: WHERE department_id = e.department_id.

-- Employee earns less than their OWN department's average
SELECT e.first_name, e.last_name, e.salary
FROM   employees e
WHERE  e.salary < (
    SELECT AVG(salary) FROM employees
    WHERE  department_id = e.department_id  -- ← correlation
);                                             -- Q29, Q151

-- Employee earns the MAX in their department
WHERE e.salary = (
    SELECT MAX(salary) FROM employees
    WHERE  department_id = e.department_id
)                                              -- Q88
ALL / ANY multi-value subqueries ▾

> ALL means greater than every value in the subquery result (equivalent to greater than the MAX). > ANY means greater than at least one value.

-- Greater than ALL salaries in dept 30 = greater than MAX(dept 30)
WHERE salary > ALL (
    SELECT salary FROM employees WHERE department_id = 30
)                                              -- Q18, Q68, Q97, Q163

-- Lower than ALL in dept 80
WHERE salary < ALL (
    SELECT salary FROM employees WHERE department_id = 80
)                                              -- Q97
Nested aggregates — MAX of AVG, MIN of COUNT ▾

Oracle allows wrapping an aggregate function around a grouped aggregate in HAVING to find extreme groups. Standard SQL uses a subquery in FROM instead.

-- Department with THE HIGHEST average salary
HAVING AVG(e.salary) = (
    SELECT MAX(AVG(salary))   -- Oracle extension
    FROM   employees GROUP BY department_id
)                                              -- Q33, Q80, Q110, Q122, Q170
Nth-highest salary pattern ▾

Classic interview pattern. Uses nested subqueries or FETCH FIRST. Each level eliminates the top N salaries.

-- 2nd highest salary
WHERE salary = (
    SELECT MAX(salary) FROM employees
    WHERE  salary < (SELECT MAX(salary) FROM employees)
)                                              -- Q53

-- 3rd highest using FETCH FIRST (Oracle 12c+)
WHERE salary = (
    SELECT MIN(salary) FROM (
        SELECT DISTINCT salary FROM employees
        ORDER BY salary DESC
        FETCH FIRST 3 ROWS ONLY
    )
)                                              -- Q109

3. JOIN — Combining Tables

Joins retrieve data spread across multiple tables. Questions use 2-table, 3-table, and self-joins.

INNER JOIN — two and three tables ▾
-- Two-table join: employees ↔ departments
SELECT e.first_name || ' ' || e.last_name AS employee_name,
       d.department_name
FROM   employees e
JOIN   departments d ON e.department_id = d.department_id; -- Q1,Q6

-- Three-table join: employees ↔ departments ↔ locations
SELECT e.first_name, l.city
FROM   employees e
JOIN   departments d ON e.department_id = d.department_id
JOIN   locations l   ON d.location_id   = l.location_id
WHERE  l.city = 'Toronto';                    -- Q30
Five-table join — reaching regions ▾
-- Spans all geographic tables: dept → location → country → region
FROM  employees e
JOIN  departments d ON e.department_id = d.department_id
JOIN  locations l   ON d.location_id   = l.location_id
JOIN  countries c   ON l.country_id    = c.country_id
JOIN  regions r     ON c.region_id     = r.region_id
WHERE r.region_name = 'Europe'               -- Q107, Q155, Q191
SELF JOIN — employees as their own managers ▾
-- INNER self join: only shows employees WITH a manager
SELECT e.first_name || ' ' || e.last_name AS employee_name,
       m.first_name || ' ' || m.last_name AS manager_name
FROM   employees e
JOIN   employees m ON e.manager_id = m.employee_id; -- Q51

-- LEFT self join: includes top-level employee (NULL manager)
FROM   employees e
LEFT JOIN employees m ON e.manager_id = m.employee_id; -- Q173

4. INSERT — Adding Data

~50 of the 200 questions are INSERT statements. All use the same structural template with variations in columns and values.

INSERT template & key variations ▾
INSERT INTO employees (
    employee_id, first_name, last_name, email,
    hire_date, job_id, salary,
    commission_pct,   -- optional: NULL or 0.15
    department_id, manager_id  -- optional: can be NULL
) VALUES (
    (SELECT MAX(employee_id) + 1 FROM employees),
    'John', 'Doe', 'JDOE',
    SYSDATE, 'IT_PROG', 6000,
    NULL,             -- commission_pct
    60, 103           -- department_id, manager_id
);

-- Job IDs used: IT_PROG, SA_REP, SA_MAN, ST_CLERK, MK_REP,
--              FI_MGR, FI_ACCOUNT, AC_ACCOUNT, PR_REP, HR_REP, AD_VP

5. UPDATE — Modifying Data

~50 UPDATE statements. Most follow two patterns: simple percentage raise, or subquery-driven updates.

UPDATE patterns ▾
-- Pattern 1: Flat percentage increase
UPDATE employees
SET    salary = salary * 1.08
WHERE  department_id = 90;             -- Q40: 8% raise for dept 90

-- Pattern 2: Job ID pattern matching
SET    salary = salary * 1.05
WHERE  job_id LIKE '%CLERK%';          -- Q17, Q141
WHERE  job_id LIKE 'ST%';              -- Q52
WHERE  job_id LIKE '%REP';             -- Q129

-- Pattern 3: Date-based update
WHERE  hire_date < TO_DATE('01-JAN-2005', 'DD-MON-YYYY');  -- Q23

-- Pattern 4: Subquery in WHERE
WHERE  department_id IN (
    SELECT department_id FROM departments WHERE location_id = 1700
)                                       -- Q171

-- Pattern 5: NVL for commission (avoids NULL arithmetic)
SET    commission_pct = NVL(commission_pct, 0) + 0.05  -- Q70, Q105

Core Conceptual Themes

Six foundational themes drive this question set. Every question maps to at least one.

Theme 1 — Data Retrieval Precision

  • Exact equality vs range comparison
  • NULL-safe filtering (IS NULL / IS NOT NULL)
  • Pattern matching with LIKE
  • Multi-condition AND / OR logic
  • Duplicate elimination with DISTINCT

Theme 2 — Relational Navigation

  • Two-table JOIN (employees ↔ departments)
  • Three-table JOIN (+ locations)
  • Five-table JOIN (+ countries, regions)
  • Self JOIN (employee ↔ manager)
  • LEFT JOIN for optional relationships

Theme 3 — Subquery Mastery

  • Scalar subqueries in WHERE
  • Correlated subqueries (per-row context)
  • Subqueries in HAVING
  • ALL / ANY set operators
  • Nested subqueries (Nth highest)
  • Subqueries in FROM (inline views)

Theme 4 — Aggregation & Grouping

  • COUNT, SUM, AVG, MAX, MIN
  • GROUP BY one or more columns
  • HAVING clause for group filtering
  • Nested aggregates: MAX(AVG()), MAX(COUNT())
  • Department vs company average comparison

Theme 5 — DML Operations

  • INSERT with all column types
  • NULL commission & manager scenarios
  • Subquery-driven INSERT values
  • Percentage-based salary UPDATE
  • Date-conditional UPDATE (TO_DATE)
  • NVL() for NULL-safe arithmetic

Theme 6 — Temporal & Pattern Filtering

  • TO_DATE() for date literals
  • TO_CHAR(date, 'MM'/'YYYY') extraction
  • SYSDATE for current timestamp
  • Job ID pattern matching (LIKE 'ST%')
  • MIN(hire_date) for earliest employee

Pattern Analysis: Recurring Structural Templates

Five repeating structural templates account for the majority of questions:

Template A — Employee attribute comparison
WHERE salary {op} (SELECT salary FROM employees WHERE employee_id = N)
Used in: Q9, Q32, Q57, Q85, Q100, Q124, Q160, Q181 and ~15 others.
Template B — Same-group as another employee
WHERE {attribute} = (SELECT {attribute} FROM employees WHERE employee_id = N) AND employee_id != N
Used in: Q5, Q16, Q65, Q76, Q82, Q106, Q142, Q160, Q190 and others.
Template C — Salary vs own department aggregate
WHERE e.salary {op} (SELECT AGG(salary) FROM employees WHERE department_id = e.department_id)
Used in: Q29, Q38, Q62, Q88, Q91, Q103, Q121, Q139, Q151, Q178, Q199.
Template D — Department headcount comparison
HAVING COUNT(...) {op} (SELECT COUNT(*) FROM employees WHERE department_id = N)
Used in: Q42, Q59, Q69, Q92, Q116, Q140, Q152, Q164.
Template E — INSERT standard structure
INSERT INTO employees (...) VALUES ((SELECT MAX(employee_id)+1 FROM employees), ..., SYSDATE, job_id, salary, commission_pct, dept_id, manager_id)
Used in all ~50 INSERT questions with column variations.
Template F — UPDATE by job ID pattern
UPDATE employees SET salary = salary * multiplier WHERE job_id LIKE 'pattern'
Multipliers: 1.05 (5%), 1.07 (7%), 1.08 (8%), 1.10 (10%), 1.12 (12%).

Key Insights for Exam Preparation

📌 Master correlated subqueries first
They appear in ~18 questions and underpin the hardest SELECT patterns. The key is recognising when each row needs to be compared to its own group (department or job). Practice with Q29, Q62, Q88, Q121, Q139.
📌 INSERT questions test column knowledge, not logic
All ~50 INSERT questions share the same structure. What varies is: which columns to include, what job_id to use, whether commission_pct is NULL or a value, and whether manager_id is present. Learn the column list once; the rest is substitution.
📌 UPDATE questions test percentage arithmetic and WHERE conditions
Most UPDATE questions are: SET salary = salary × (1 + pct/100) plus a WHERE clause filtering by department, job ID LIKE pattern, hire date, or manager. The NVL() function is essential when updating commission_pct to avoid NULL propagation.
📌 JOIN path: employees → departments → locations → countries → regions
Learn this five-table chain. Questions about cities (Q30, Q56, Q66) need 3 tables. Questions about continents (Q107, Q191) need all 5. The join keys are: department_id, location_id, country_id, region_id.
